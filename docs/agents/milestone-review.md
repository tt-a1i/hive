# 深度审查流程

触发条件由根 [AGENTS.md](../../AGENTS.md) 定义。小改不自动触发。

## 派发

同时派 4 个独立 reviewer，各自读取真实 diff 与相关实现，不共享中途结论。
实质正确性审查按根指令选模型，显式用户偏好优先，不为评分无依据升级模型。
在 Hive PTY 内由 Orchestrator 使用 `team review`（先查 `team guide` 参数），
需要指定成员时用 `team spawn --ephemeral` + `team send`；Worker 报回审查需求。
其他环境用所用工具的子代理机制。完全不支持时，用 4 次独立 review prompt，
交付明确说明限制。

每个 prompt 包含：

- Hive 项目背景、当前阶段、任务目标与原始清单、改动范围和 diff 基准。
- `docs/superpowers/specs/2026-04-18-hive-design.md`，以及覆盖它的现行
  `CONTEXT.md`、`docs/design-decisions.md` 与任务内协作修订路径。
- 本维度检查项、之前 review 的问题列表（首轮没有则注明）。
- 要求只列问题、严重程度、触发条件和文件:行号，不罗列优点；逐条验证旧问题
  是否已修。每份报告 ≤400 字，附 A–F 评分；无证据不凑问题。

## 四个维度

| 维度 | 必查项 |
|---|---|
| A 架构与可维护性 | 模块职责、体积增长、耦合、路由注册、前端状态归属、后续扩展阻塞 |
| B 真实 bug 与边界 | 内存/DB 一致、异常、DB/PTY 资源回收、启动期 stop、onExit 重入、ID |
| C 测试质量 | 测试污染生产代码、循环 mock、无效断言、错误路径、真实穿透与覆盖盲区 |
| D 现行规范对齐 | snake_case、三态、消息账本、水位、成员 name、角色权限、用户目标遗漏 |

## 处理与复审

每条反馈标记：修复（文件:行号与验证）/ 部分（剩余影响）/ 不修（依据与风险）。
每条严重项必须处理，不可用“下次再说”代替。审查结论冲突时，记录冲突与裁决依据。
任一维度 ≤C+，先修复再让相应 reviewer 复审，直到全部 ≥B- 才可交付。
评分仅表示本次限定范围，不代表整个产品质量或旧 MVP 完成度。

最终报告保留 `## Self-Review`，列四维问题摘要（每条一行）、严重项 verdict、
综合评分和一句范围结论；若复审，附修复前后对比。
